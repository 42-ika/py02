## 第I章：はじめに

農業データエンジニアリングの世界へようこそ！

Pythonの基礎（Module 00）と庭の監視用クラス（Module 01）を学んだ皆さんは、スマート農業における実際の課題に取り組む準備ができています。現代の農業では、灌漑システムを流れる水のようにデータが流れています。センサーの測定値が絶えず届き、天気APIが予報を提供し、IoT機器が土壌のpHから温室の湿度まで、あらゆるものを監視します。

しかし、このデータパイプラインに問題が起きたらどうなるでしょうか？ 収穫期にセンサーが故障したら？ 重要な監視期間中にネットワーク接続が切れたら？ 破損したデータによって、誤った灌漑サイクルが開始されそうになったら？

プロの農業データエンジニアは、堅牢なシステムとは障害を避けるためだけに作られるものではなく、**予期しない事態に適切に対処できるよう設計されるもの**だと知っています。デジタル温室にも、自然そのものと同じくらいの回復力が必要です。

Pythonの例外処理システムは、障害に強い農業データパイプラインを構築するための道具です。センサーの異常を捕捉し、農業向けの独自アラートを作成し、自然の猛威（あるいはマーフィーの法則）に見舞われてもデータの整合性を確保する方法を学びます。

このプロジェクトを通して、基本的なプログラマーから農業データエンジニアへと成長し、予期しないことが起きても稼働し続ける監視システムを構築します。

Garden Guardian：スマート農業のためのデータエンジニアリングへようこそ！

これまでのプロジェクトで学んだ庭の監視の基礎をもとに、農業システム向けの、障害に強いデータパイプラインを設計・構築するための重要なスキルを身につけます。

## 第VII章：演習2 — さまざまな種類の問題

| 項目 | 指定 |
| --- | --- |
| 演習 | Exercise 2：`ft_different_errors` |
| ディレクトリ | `ex2/` |
| 提出ファイル | `ft_different_errors.py` |
| 許可される関数 | `print()`, `open()`, `int()` |

庭のプログラムでは、さまざまな種類の問題が起こる可能性があります。Pythonには状況に応じた異なる種類のエラーがあり、それぞれ個別に、またはまとめて捕捉できます。

誤りのあるコードを含む関数 `garden_operations(operation_number)` を作成してください。`operation_number` が0から3までの各値のとき、それぞれ異なる誤ったコードを実行し、以下の例外のいずれかを発生させます。

- `ValueError`：不適切なデータが与えられた場合（例：`int()` に数値の代わりに `"abc"` を渡す）。
- `ZeroDivisionError`：ゼロで除算しようとした場合。
- `FileNotFoundError`：存在しないファイルを開こうとした場合（開かれていなければ、`close()` する必要はありません）。
- `TypeError`：組み合わせられない異なる型を混在させようとした場合（文字列と数値を足そうとするとどうなるでしょうか？）。

`operation_number` がそれ以外の値の場合は、誤りのあるコードを実行せず、そのまま戻ってください。

次のことを行う関数 `test_error_types()` を作成してください。

- 各種類のエラーが発生する様子を示す。
- 各エラーを捕捉し、何が問題だったかを説明する。
- 各エラーの後もプログラムが実行を続けることを示す。
- 1つの `try:` ブロックで、複数のエラー型を捕捉する方法を示す。

### 実行例

```text
$> python3 ft_different_errors.py
=== Garden Error Types Demo ===
Testing operation 0...
Caught ValueError: invalid literal for int() with base 10: 'abc'
Testing operation 1...
Caught ZeroDivisionError: division by zero
Testing operation 2...
Caught FileNotFoundError: [Errno 2] No such file or directory: '/non/existent/file'
Testing operation 3...
Caught TypeError: can only concatenate str (not "int") to str
Testing operation 4...
Operation completed successfully

All error types tested successfully!
```

> なぜPythonには異なる種類のエラーがあるのでしょうか？ 1つの `try:` だけで複数の種類のエラーを捕捉するにはどうすればよいでしょうか？ `type()` は使えないことに注意してください。

> `TypeError` を発生させる誤ったコードに対して、mypyはエラーを表示します。それがmypyの役割です！ この例外をテストするため、この誤りは意図的に残す必要があります。

> `open()` はCですでに使ったことがあるはずです。Pythonでの使い方はとても簡単です。

Pythonの組み込みエラーだけでは、庭のプログラムに必要な具体性が足りないことがあります。独自のエラー型を作れば、コードをより明確で役立つものにできます。

- `GardenError`：庭の問題に関する基本的なエラー。
- `PlantError`：植物の問題に関するエラー（`GardenError` を継承する）。
- `WaterError`：水やりの問題に関するエラー（`GardenError` を継承する）。

各独自例外は、次の条件を満たす必要があります。

- `Exception`（または `GardenError`）を継承したシンプルなクラスであること。
- メッセージが指定されなかった場合に使う、固有のデフォルトエラーメッセージを持つこと（例：`"Unknown plant error"`）。

次のことを行う関数を作成してください。

- 異なる状況で独自のエラーを送出する。
- 特定の独自エラー型を捕捉する方法を示す。
- `GardenError` を捕捉することで、庭に関するすべてのエラーを捕捉できることを示す。

### 実行例

> Pythonの組み込みエラーを使う代わりに、独自のエラー型を作るべきなのはどのような場合でしょうか？ 継承は、異なる種類のエラーを整理するうえでどのように役立つでしょうか？

## 第IX章：演習4 — finallyブロック：必ず後片付けする

| 項目 | 指定 |
| --- | --- |
| 演習 | Exercise 4：`ft_finally_block` |
| ディレクトリ | `ex4/` |
| 提出ファイル | `ft_finally_block.py` |
| 許可される関数 | `print()`, `str.capitalize()` |

庭のプログラムでは、エラーが発生してもリソースを後片付けする必要があります。`finally` ブロックはこの用途に最適です。エラーの有無にかかわらず、常に実行されます。

次の処理を行う関数 `water_plant(plant_name)` を作成してください。

- 植物への水やりを試みる。
- 植物名の先頭が大文字になっていれば成功する。
- 植物名の先頭が大文字になっていなければ、エラーを送出する（前の演習で作成した `PlantError` 例外を使用する）。
- 成功した場合にメッセージを表示する。

次の処理を行う関数 `test_watering_system()` を作成してください。

- 水やりシステムを開く（メッセージを表示するだけ）。
- `water_plant()` を使って複数の植物に水をやる。
- `try/except/finally` 構造を使用する。
- 植物名が無効で水をやれない場合にエラーを処理する。その場合はテストを停止し、直ちにメインへ戻る。
- `finally` ブロックで、水やりシステムを必ず閉じる。
- エラーが発生しても、後片付けが必ず行われることを示す。

### 実行例

```text
$> python3 ft_finally_block.py
=== Garden Watering System ===

Testing valid plants...
Opening watering system
Watering Tomato: [OK]
Watering Lettuce: [OK]
Watering Carrots: [OK]
Closing watering system

Testing invalid plants...
Opening watering system
Watering Tomato: [OK]
Caught PlantError: Invalid plant name to water: 'lettuce'
.. ending tests and returning to main
Closing watering system

Cleanup always happens, even with errors!
```

> エラーが発生した場合でも、リソースを後片付けすることが重要なのはなぜでしょうか？ `finally` ブロックは、後片付けが必ず行われるようにするうえで、どのように役立つでしょうか？
